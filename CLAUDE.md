This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Minimal training code for a small Chinese "Future-Anchored Order-Free" (FAOF) language model. Despite the directory name, the current implementation is intentionally **dense, not MoE** — the point is to validate the auxiliary-loss idea before adding routing complexity. Uses `uv` for environment management; dependencies are just numpy, torch, tqdm. There are no tests and no linter configured.

## Commands

All Python runs go through `uv run`. Everything is driven by a single JSON config file (see `configs/`).

```bash
uv sync                                                        # install deps into .venv

# End-to-end smoke test (toy corpus → tokenizer → bins → train → eval)
uv run python scripts/make_toy_corpus.py --out data/toy.txt --docs 4000
uv run python scripts/build_char_tokenizer.py --input data/toy.txt --out data/tokenizer.json --vocab-size 3000
uv run python scripts/tokenize_text.py --input data/toy.txt --tokenizer data/tokenizer.json --out-dir data/bin --val-ratio 0.02
uv run python -m faof.train --config configs/smoke.json
uv run python -m faof.eval --config configs/smoke.json --ckpt runs/smoke/ckpt_last.pt

# Generation / interactive REPL against a trained checkpoint
uv run python -m faof.generate --config <cfg.json> --ckpt <ckpt.pt> --prompt "..."
uv run python -m faof.chat --config <cfg.json> --ckpt <ckpt.pt> --mode faof --show-anchors

# Ablation: generate A/B/C/D configs from a base config, then train+eval all four
uv run python scripts/make_ablation_configs.py --base configs/smoke.json --out-dir configs/ablation_smoke --run-root runs/ablation_smoke --max-steps 60
bash scripts/run_ablation.sh configs/ablation_smoke

# Chinese Wikipedia data prep (small shard variant; full pipeline in README)
bash scripts/prepare_zhwiki_small.sh data/zhwiki_small
```

`data/` and `runs/` are gitignored — corpora, tokenizers, .bin files, and checkpoints are all local artifacts regenerated by the scripts above.

## Architecture

Pipeline: raw text → `CharTokenizer` (char-level, whitespace stripped, JSON with 4 specials) → flat binary token files (`train.bin`/`val.bin`, uint16 if vocab ≤ 65535, read via `np.memmap`) → training.

**The model (`src/faof/model.py`)** is a standard causal decoder (pre-LN blocks, SDPA attention, SwiGLU MLP, learned positional embeddings, weight-tied next head) plus three auxiliary head families that define FAOF:

- `anchor_heads` — one linear head per offset in `offsets` (default 2/4/8/16), predicting the token exactly k steps ahead of each position.
- `order_free_head` — multi-label prediction (BCE) of the *set* of tokens in the next `future_window` positions, computed only at randomly sampled `order_positions`.
- Bridge — `bridge_forward` conditions on (current hidden state, current token embedding, a **soft anchor** = probability-weighted mixture of the top-m anchor-head token embeddings, and a span-length embedding) via `bridge_mlp`, then decodes the intermediate span between the current position and the future anchor at randomly sampled positions/offsets.

**Config flow:** a single JSON file deserializes into `TrainConfig` (`src/faof/config.py`), which holds run/optimizer/model/loss-weight fields together. All four entry points (`train`, `eval`, `generate`, `chat`) rebuild `ModelConfig` from `TrainConfig` the same way, with `vocab_size` taken from the tokenizer at load time — if you add a model hyperparameter, thread it through all four. Checkpoints (`ckpt_last.pt`) store `{model, config, step[, optimizer]}`; `init_from` loads weights only, `resume_from` also restores optimizer state and step count.

**Why batches are longer than block_size:** `BinaryTokenDataset` samples `block_size + extra_tokens` tokens per sequence, where `TrainConfig.extra_tokens = max(max(offsets), future_window)`. The model only sees the first `block_size` tokens; the tail exists so anchor/order/bridge targets at the last positions are always defined. Keep this invariant in mind when touching `loss_fn` in `train.py` or the metrics in `eval.py` (they slice `full_ids` with the same offset arithmetic).

**Loss** is a weighted sum `next_weight·CE + anchor_weight·CE + order_free_weight·weighted-BCE + bridge_weight·CE`; the ablation convention (configs `A_baseline` → `D_anchor_order_bridge`) turns these weights on cumulatively. `order_free_neg_weight` down-weights negative classes in the BCE since the target set is tiny relative to the vocab.

**Generation modes (`chat.py`):** `next` is ordinary autoregressive sampling; `faof` alternates bridge-decoding `anchor_offset - 1` tokens with sampling an anchor token from the anchor head, so text is produced anchor-first rather than strictly left-to-right.

Device selection is `auto` (cuda → mps → cpu); dtype (`float32`/`float16`/`bfloat16`) drives both model params and an autocast context, and `activation_checkpointing` is available for larger runs.
